# V.Canvas・酒馆剧情插画助手

> 文字负责讲述，画面负责定格。V.Canvas 在酒馆对话中默默守望 —— 剧情里出现值得画的瞬间，它就把这一帧画出来，嵌进对应段落正下方；没有值得画的瞬间，就安静跳过。故事照常聊，画面悄悄补。

光有文字的故事总像少了点什么：角色长什么样、战斗场面有多燃、告白那一刻的光线，都只能靠脑补。V.Canvas 就是为把「脑补」变成「亲眼看到」而生的 —— 它不打扰你的对话节奏，只在恰到好处的时候递上一张图。



```
（AI 讲了一段剧情……）

\\\\\\\\\\\\\\\[ILLUST: a silver-haired girl standing on a rainy neon street | 1girl, silver hair, cyberpunk, neon lights, rain]

↓ 插件捕获标记 → 出图 → 就地替换成

（AI 讲了一段剧情……）

!\\\\\\\\\\\\\\\[Illustration]\\\\\\\\(/user/images/xxx.png)

（AI 后续文字被图挤到下方继续排列……）
```

## 它能做什么

### 🖼️ 自动配图：值得画的瞬间，一张不落



* **标记驱动，就地成图**：剧情模型在正文中输出 `[ILLUST: 描述 | Tags]` 标记，插件捕获后即在该段正下方出图。图片随段落走、后续文字顺延，轻小说式图文交错。

* **不占上下文**：标记出图后自动从消息中剔除，插图只走显示层，不进 AI 上下文、不占 Token。

* **一次多张，节奏自控**：单轮最多可规划多张图，默认串行逐张生成（不触发上游风控），也可开启并行、先回先插。

* **失败不残留**：某张失败时标记原样保留、已出图不重画，错误原因直接透传显示，绝不静默。

### 🧭 双路线配图：再顽固的模板也有图



* **标记驱动（主路线）**：剧情模型配合时零额外等待，识别到标记即出图。

* **上下文出图（备用路线）**：正文没有标记时，由单独配置的分析模型通读正文与前文，自动产出提示词与插入位置，再走同一条出图链路 ——**不依赖剧情模型的输出格式**，对任何角色卡都适用。

* **并存且不重复**：有标记走标记、无标记才分析，两条路线共用同一套出图设置，自动衔接。

### 🎛️ 提示词：全自动，也可全可控



* **两段式标记**：自然语言描述与 Danbooru 标签同时产出，天然适配两类上游。

* **按链路分流**：`auto / description / tags / both` 四档，决定把哪一半送给上游 —— 经适配服务送描述、直连官方 NAI 送标签，缺一半自动回退。

* **质量词与负面词**：内置默认，随时可改。

* **点击看图**：点击任意插图，浮层即显示这张图所用的描述与标签；提示词随聊天记录保存，刷新、切换聊天都不丢。

### 🔌 出图渠道：专注 NovelAI 协议



* **V.Adapter 适配服务（推荐）**：把 OpenAI 上游封装为 NAI 协议，插件只填服务地址即可，默认 `http://127.0.0.1:8888`。

* **官方 NovelAI / NAI 网关**：直连，模型名手填（如 `nai-diffusion-4-5-full`）。

* **其他 NAI 兼容服务**：实现 `POST {base}/ai/generate-image` 且返回 ZIP 即可接入。

* **画风由上游决定**：经适配服务时取服务端画风配置；直连时随提示词标签送出。插件不设画风选项，专注把标记变成图。

### 📁 图片管理：随聊随存，台账一目了然



* **内嵌楼层卡片**：图片插在对应段落正下方，与剧情一一对应。

* **完整生成记录**：所有出图按时间倒序记录，跨聊天不丢失，可随时清空；「概览」页另显示当前聊天的出图缩略图。

* **绘制过程可见**：顶部进度悬浮卡片实时显示「分析中 → 绘制 n/N → 完成 / 失败」，可随时「终止」，失败原因直接可见，不会静默。

* **格式兼容**：png /jpg/webp 均可，适配不同网关的输出格式。

### ⚙️ 设置：细到每一步都可调



* **六页管理面板**：概览、生成记录、提示词、转译出图、上下文出图、设置，全部集中一处，改动即时保存。

* **触发规则可调**：每轮上限、并行 / 串行、swipe 重配、剔除 tag、忽略的消息类型。

* **规则注入可控**：注入位置（`in_chat` / `in_prompt`）与深度可调，兼容各种角色卡模板。

* **排障友好**：控制台详细日志开关、一键恢复默认。

### 🧪 开发者友好



* **离线自测**：不依赖酒馆即可跑通「NAI 协议 → ZIP → base64」与标记解析 / 就地替换全分支。

* **契约检查**：设置字段与面板控件一一对应，新增设置项忘记加控件会直接报错。

## 小贴士



* **开箱即用**：配好上游地址与模型即可自动配图；想先只写 tag 不出图，关掉「启用自动插画」即可。

* **共享网关注意节奏**：建议将每轮上限设为 1，避免触发频率限制。

* **重度「沙盒卡」**：保持默认的 `in_chat` + 深度 `0` 注入；仍不生效就把规则加进该卡自己的世界书。

* **上下文出图**：默认关闭；开启前先在面板填好分析模型的地址与模型名。

* **图片数据跟着聊天走**：删除聊天即删除对应图片数据。

## 一、前置依赖

本扩展**仅使用 NovelAI 协议**，自身不直连任何 OpenAI 上游。因此出图前，需先运行一个

**NovelAI 协议服务**，插件只需填写该服务的地址：



| 上游类型                   | 说明                                                                                                            |
| ---------------------- | ------------------------------------------------------------------------------------------------------------- |
| **V.Adapter 适配服务**（推荐） | 用户自己的适配服务，默认 `http://127.0.0.1:8888`，将 OpenAI 上游封装为 NAI 协议                                                    |
| **官方 NAI / NAI 网关**    | 地址直接填网关或 `https://image.novelai.net`，模型名需手填（如 `nai-diffusion-4-5-full`）。**NAI 非 OpenAI 格式，不可经 V.Adapter，须直连** |
| 其他 NAI 协议兼容服务          | 只要实现 `POST {base}/ai/generate-image` 且返回 ZIP 即可                                                               |

> **画风由上游决定，本插件不设画风选项。**
> 经 V.Adapter 出图时，画风取自
> **服务端插件**
> （
> `<SillyTavern>\plugins\V.Adapter\data\`
> ，在
> `http://127.0.0.1:8888`
> 面板维护）那份配置 ——
> V.Adapter 的
> **酒馆扩展面板**
> 里的画风只作用于它自己的
> `/vgen`
> 命令，与本插件无关。
> 直连官方 NAI / NAI 网关时，画风随提示词（标记中的标签段）一起送出。

### ⚠️ 使用第三方 NAI 网关的注意事项



1. **「测试连接」按钮可能失败，但不代表服务不可用。** 多数网关仅放行出图接口

   （`generate-image`），订阅端点被屏蔽。**以「生成记录」中是否存在成功条目为准。**

2. **必须发送完整参数集。** 仅发送 `input/model/action/parameters{宽高,步数,负面词}` 这类最小集，

   网关会返回 `400 无效的请求`。本插件发送一整套 NAI 4.x 参数（含 `params_version`、

   `sampler`、`noise_schedule`、`v4_prompt` 等），对官方 NAI / 网关 / V.Adapter 均适用。

3. **配额与频率**：共享网关通常限制「每日 N 次 + 每分钟 N 次」，而自动插画属于重负载。

   建议将**每轮上限设为 1**，避免作为压测请求源。

4. **不建议启用参考图 / 氛围图，每次请求仅生成一张。** 本插件本身即逐张串行、`n_samples: 1`。

5. 出图体积可能为数百 KB 至 2 MB，格式可能为 **webp**（插件已支持 png/jpg/webp）。

> 为何不支持 OpenAI 直连：若支持直连，用户仅凭一个 Key 即可出图，中间的协议转换服务将失去存在意义。
> 本插件与 V.Adapter 为配套关系，分工明确。

## 二、安装

### 方式一：从仓库安装（推荐）

1. 打开酒馆 → 顶部「扩展」面板（三个方块图标）
2. 点「安装扩展」
3. 粘贴仓库地址 `https://github.com/VVVVVILK/V.Canvas-ST.git` → 安装
4. 完成后扩展列表出现「V.Canvas」，刷新页面即可使用

### 方式二：手动复制

将本文件夹整体复制到酒馆的扩展目录，并重命名为 `V.Canvas`：



```
\\\\\\\\\\\\\\\<SillyTavern>/data/\\\\\\\\\\\\\\\<user-handle>/extensions/V.Canvas/

├── manifest.json

├── index.js

├── style.css

├── panel.html          管理面板（独立前端，经桥接控制扩展本体）

├── README.md

└── lib/

\\\\\\\&#x20;   ├── marker.js      \\\\\\\\\\\\\\\[ILLUST:...] 标记的捕获与就地替换

\\\\\\\&#x20;   ├── nai-api.js     NovelAI 协议调用 + ZIP 解包

\\\\\\\&#x20;   └── settings.js    设置的校验与持久化
```

随后**重启酒馆**（或刷新页面），「扩展」面板中会出现 **V.Canvas**。



* 访问路径：`/scripts/extensions/third-party/V.Canvas/`

* 依赖：无（ZIP 解压使用酒馆自带的 `/lib/jszip.min.js`，无需额外安装库）

## 三、管理面板（所有设置均在此处）

安装完成后，酒馆的扩展面板中会出现如下条目：



```
V.Canvas      v0.1.0

\\\\\\\&#x20;       \\\\\\\\\\\\\\\[ 打开管理面板 ]
```

点击「打开管理面板」即可打开管理面板 —— 一个全屏深色控制台（左侧导航、卡片式排版）。

由于酒馆抽屉空间有限，无法容纳全部字段，故集中置于面板中。

面板包含六页：



| 页         | 内容                                                                                                                                                   |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **概览**    | 自动插画是否开启、当前上游、本聊天已出图数量（缩略图）、触发规则摘要                                                                                                                   |
| **生成记录**  | 本插件出过的全部插画，按时间倒序。记录持久化在酒馆设置中，切聊天不丢失，可清空                                                                                                              |
| **提示词**   | 正面质量提示词、负面提示词、画风、破限词（选填）—— 交由分析模型遵守，长度不限，见 5.3                                                                                                       |
| **转译出图**  | 输入一句简短描述 → 由适配服务扩写为完整画面提示词 → 出图；结果仅在面板内展示，不写入聊天记录                                                                                                    |
| **上下文出图** | 另配一个文字模型阅读正文与前文，产出提示词后由当前出图上游作画。**不依赖剧情模型配合**                                                                                                        |
| **设置**    | 总开关、上游地址 / Key / 模型、提示词形态、出图参数（并行开关 / 宽高 / 步数 / CFG / 负面词 / 上限 / 超时 / 间隔）、触发规则（swipe 重配、剔除 tag、忽略类型）、提示词注入（开关 / 位置 / 深度 + 规则文本 + 一键复制）、进阶（调试日志、恢复默认） |

> 「概览」的缩略图只反映
> **当前这条聊天**
> ；「生成记录」是跨聊天的完整台账，两者用途不同。

### ⚠️ 面板与后端的职责边界



* 面板是**独立的一页**，无法读取或修改酒馆的内部状态；

* 面板发起的每个动作，均由面板发送指令给**酒馆页面内的扩展本体**执行，

  扩展实际执行数据修改 → 刷新消息 → 落盘，随后将结果回传面板显示。

因此不存在「面板已修改而酒馆未变更」的情况 —— 面板自身不具备修改能力，

只能请求扩展执行。反之，若桥接无法建立（扩展加载失败），

面板会**直接以红字告警**，而非停留在不可用状态。

改动**即时保存**（字段失焦即写入），保存成功会显示「已保存并生效」提示。

### 修改后未生效的处理

酒馆对扩展的 JS/CSS 存在缓存。修改代码后若面板无变化，可使用 **Ctrl+F5 强制刷新酒馆页面**。

## 五、标记与送出内容（prompt\_format）

### 5.1 怎么让 AI 输出标记

两种方式，任选其一：



1. 打开设置中的「自动把 ILLUST 规则交给模型」开关（默认已开）；或

2. 点击「复制规则」，将规则文本粘贴进角色卡的描述 / 系统提示词，或角色卡的**世界书**中。

**注入位置的选择（先看这一节，能省掉大量排查）**



| 取值                         | 效果                    | 何时用          |
| -------------------------- | --------------------- | ------------ |
| `in_chat` + 深度 `0`（**默认**） | 规则作为对话内的系统消息，插在模型回复之前 | 绝大多数情况       |
| `in_prompt`                | 规则并入主系统提示词（整段提示词的最前面） | 预设已自行处理格式约束时 |

⚠️ **重度「沙盒卡」（世界书里带整套输出模板的卡）应保持默认的&#x20;**`in_chat`**&#x20;+ 深度&#x20;**`0`**。**

这类卡会在世界书的 `depth 0` 注入状态栏、思维链、输出规则等一大批硬格式约束，

位置紧贴模型回复之前。写在主系统提示词里的规则会被这些模板盖过 ——

表现为**模型照常出剧情，但一个标记都不写**（插件因此完全不动）。

把它们放在同一深度，模型才会认真对待。

若 `in_chat` + 深度 `0` 仍不生效，说明该卡的模板约束过强，

请用「复制规则」把规则**加进该卡自己的世界书**（例如它定义输出格式的那一条里），

这样标记就成为它模板的一部分，而不再是一条来自外部的 "额外要求"。

规则示例（每轮上限 2 张）：



```
若情节出现显著的场景切换、角色外观变化或高张力画面，请在对应段落正下方另起一行输出标记：

\\\\\\\\\\\\\\\[ILLUST: 自然语言描述 | Danbooru,Tags]

标记须遵守下列要求：

1\\\\\\\\. 两段都必须填写，以 | 分隔，不得省略其中任一段。

2\\\\\\\\. 描述段用自然语言书写，须覆盖角色外貌特征、服装与道具、动作姿态、场景环境、构图与镜头、画风。

3\\\\\\\\. 标签段用英文 Danbooru Tag，以英文逗号分隔，按「主体、外观、服装、动作、场景、风格」的顺序排列。

4\\\\\\\\. 单个标记须自足：应包含该画面完整的主角特征与场景信息，不依赖其他标记补全。

5\\\\\\\\. 一轮输出多个标记时，各标记须针对不同的画面时刻，并分布在正文的不同位置（例如中段与末段），不得集中在一处，也不得重复描述同一画面。

6\\\\\\\\. 画面构思与剧情正文在同一次生成中一并完成，无需等待额外步骤。

7\\\\\\\\. 标记写在正文叙事段落的正下方，不要写在状态栏、思考块、表格等结构化区块内部；若正文被包裹在某个标签中（如 \\\\\\\\\\\\\\\<story\\\\\\\\\\\\\\\_scene>），标记写在标签内的对应段落下方。

单次回复最多输出 2 个标记，每个标记对应一张插画，分别插在各自段落正下方。
```

标记的容错范围：全角冒号、缺失 `|`、多余空格、标记内换行均可识别。

### 5.2 两半分别送给两类上游

标记的两半对应两类上游所需的输入形态，**因此两段都必须写**：



| 上游类型                               | 有效输入形态      | 取用标记的哪一半    |
| ---------------------------------- | ----------- | ----------- |
| 官方 NovelAI / NAI 网关（扩散模型）          | Danbooru 标签 | `\|` 之后的标签段 |
| V.Adapter 等适配服务（OpenAI 格式上游，含聊天模型） | 自然语言        | `\|` 之前的描述段 |

「送给上游的内容」设置项决定实际送出哪一部分：



| 取值             | 送出内容                                                                     | 适用场景                      |
| -------------- | ------------------------------------------------------------------------ | ------------------------- |
| `auto`（**默认**） | 地址为 `127.0.0.1` / `localhost` / `:8888`（即经 V.Adapter 转发）→ 送描述；其余地址 → 送标签 | 覆盖两条链路的常规用法               |
| `description`  | 始终送描述段                                                                   | 经 V.Adapter 走 OpenAI 格式上游 |
| `tags`         | 始终送标签段                                                                   | 直连官方 NovelAI / NAI 网关     |
| `both`         | 描述段与标签段以「描述，标签」顺序合并送出                                                    | 不确定上游类型时的保险选项             |

任一档在对应部分缺失时，自动回退到另一部分，不会送出空串。

> 说明：描述段与标签段由 AI 在撰写正文的同一次生成中一并产出，
> **不产生额外的模型调用或等待**
> 。
> 按链路分流只是从标记中取用不同的部分，运行期开销为一次字符串选择。

### 5.3 备用路线：上下文出图（不依赖剧情模型配合）

标记驱动的前提是**剧情模型愿意写标记**。部分角色卡（尤其是世界书里塞了整套输出模板的

「沙盒卡」）会用大量硬格式约束占满输出，模型只认自己那套模板，外部注入的规则一律不照做 ——

表现为**剧情照常推进，但一个标记都不写**，插件完全不动。

「上下文出图」正是为此准备的备用路线：



```
角色回复生成完毕

\\\\\\\&#x20;  └─ 正文里没有标记？

\\\\\\\&#x20;       └─ 是 → 交给「分析模型」（面板里单独配置的 OpenAI 兼容模型）

\\\\\\\&#x20;            └─ 它阅读正文 + 前文，产出若干画面：desc（自然语言）+ tags（Danbooru）+ anchor（原文引句）

\\\\\\\&#x20;                 └─ 插件把结果转成 \\\\\\\\\\\\\\\[ILLUST: desc | tags] 标记，插到 anchor 所在段落正下方

\\\\\\\&#x20;                      └─ 之后完全复用既有链路：出图 → 就地替换 → 正文不留文字
```

要点：



| 项        | 说明                                                                                             |
| -------- | ---------------------------------------------------------------------------------------------- |
| 与标记路线的关系 | **并存且不重复**。正文已有标记时走标记路线（零额外等待）；没有标记时才调用分析模型                                                    |
| 依赖       | 只需要一个可用的 OpenAI 兼容模型。**与角色卡的输出格式无关**，因此对任何卡都适用                                                 |
| 产出形态     | 每个画面同时产出 desc 与 tags，再由「提示词形态」决定送哪一半 —— 经 V.Adapter 与直连官方 NAI / 网关两条链路都能用                      |
| 提示词要求    | 「提示词」页填写的正面质量提示词、负面提示词与画风随每次请求发送。正面与画风为强制约束，负面为排除项；其中的措辞与标签由分析模型直接沿用，需要补充的细节由它自行补全             |
| 代价       | 多一次模型调用 + 一次出图，单条回复约增加 10\~30 秒（分析）+ 每张 30\~60 秒（出图）                                           |
| 张数       | 由「设置」页的**每轮上限**统一控制，与标记驱动路线共用同一设置项；设为 2 即生成 2 张、设为 3 即 3 张                                     |
| 插入位置     | 由分析模型给出的 `anchor`（原文引句）决定，插在该句所在段落的正下方。多张时要求分别取自正文的前段、中段与末段，不得全部集中在开头；引句定位容错空白差异，定位失败的画面退到正文末尾 |
| 就地验证     | 面板提供了「分析并出图」按钮，可立刻对当前最后一条角色回复跑一次，不必等下一轮对话                                                      |

**多张插画的落位顺序**：默认串行生成（一张完成再请求下一张）；「设置」页的**并行出图**开启后

改为同时发起。两种模式下每张出图成功后都会**立即单独插入正文**，不等其余 ——

第一张出图完成后即出现在正文中，不受其余张数影响。尚未出图的标记不会以文本形式留在正文里。

**分析请求是一次性窗口**：每次请求都是一份全新的两轮 messages（`system` + 一条 `user`），

不携带历史轮次。请求内容由「提示词页填写的三栏 + 前文摘要 + 本次正文」组成，

前文摘要固定取最近若干条、每条截断到固定字数 —— 第 10 轮与第 100 轮发出去的量相同，

不会随对话变长而变慢。

**产出规模**：每个画面的 `desc` 为 500\~600 字连贯自然语言，`tags` 为 300\~400 字符英文 Danbooru

标签串。请求的输出预算按画面数自动放大，不会在第二个画面处被截断。

⚠️ 该功能默认关闭。开启后请先确认「分析模型」的地址与模型名已填写，

并可用「测试连接」验证；未配置时插件只会在控制台提示，不会发起请求。

## 六、响应处理（优先直出图片，不解包）

适配服务返回什么，插件即按什么处理，**优先走无需解包的路径**：



| 响应                                  | 处理                                                                                |
| ----------------------------------- | --------------------------------------------------------------------------------- |
| **二进制图片流**（`Content-Type: image/*`） | **直接取字节使用**，不解包。插件请求携带 `Accept: image/*`，经 V.Adapter 即走此路径                        |
| 裸图字节（Content-Type 不准）               | 按文件魔数识别，同样不解包                                                                     |
| ZIP                                 | 兼容分支：使用酒馆自带的 `/lib/jszip.min.js` 解出第一张图。**官方 NovelAI 与其他 NAI 服务仅返回此格式**，保留该分支方可通用 |
| JSON                                | 取 `message` 作为错误抛出；防御性地亦识别 `b64_json`                                             |

> 为何保留 ZIP 分支：ZIP 是
> **NovelAI 协议的响应格式**
> ，并非本插件附加的封装层。
> 移除该分支后，插件将仅能配合自有适配服务使用。
> 常规（经 V.Adapter）路径不会进入解包步骤。
> 为何最终 URL 不使用
> `URL.createObjectURL(blob)`
> ：object URL 为
> **临时**
> 地址，
> 刷新页面即失效，而插图必须写入聊天记录、刷新后依然保留（验收第 10 条）。
> 故取得字节后统一通过
> `saveBase64AsFile()`
> 落盘至酒馆的图片目录（如
> `/user/images/<角色名>/xxx.png`
> ），
> 消息中保存该稳定 URL —— 这是「原地插入」得以长期成立的前提。

### 6.1 非标准扩展参数

自动插画流程只使用标准 NovelAI 协议，不附加任何非标准参数。有下列两处例外，均以查询串传递，

**收到它们的服务才会响应，其他 NAI 服务会直接忽略**：



| 参数         | 使用者         | 含义                                                                    |
| ---------- | ----------- | --------------------------------------------------------------------- |
| `expand=1` | 本插件的「转译出图」页 | 请求上游先把 `input` 扩写为完整画面提示词再出图。仅 V.Adapter 实现；扩写由上游的聊天模型完成，本插件不持有聊天模型凭据 |

配套的响应头（由 V.Adapter 回传，其他服务不提供）：



| 响应头               | 含义                                |
| ----------------- | --------------------------------- |
| `X-Illust-Via`    | 实际生效的出图链路（标准接口 / 聊天兜底）            |
| `X-Illust-Prompt` | 实际送入上游的提示词（URL 编码），用于在面板中核对扩写结果   |
| `X-Illust-Expand` | 扩写状态：`ok` / `fallback`（失败并回退为原样送） |

扩写失败不会中断出图 —— 上游会回退为原样送出输入，并在生成记录中留一条 `expand` 条目。

## 七、绘制中的占位符

检测到 tag 后，插件会在**正文内原 tag 所在位置**显示「正在绘制插画 … 约 30\~60 秒」，

出图完成后整条消息重新渲染，占位符自动替换为真实图片。

⚠️ 此占位符**仅修改 DOM、绝不写入聊天记录**。若写入 `mes`，一旦生图失败或用户刷新，

记录中将永久保留「正在绘制…」文本，且无任何机制将其替换。

### 7.1 进度悬浮卡片

除行内占位符外，插件还会在页面顶部显示一张**进度悬浮卡片**，分析 / 绘制期间常驻，

显示当前阶段并带有 \*\*「终止」按钮 \*\*：



```
┌──────────────────────────────────────────────┐

│ \\\\\\\\\\\\\\\[Vi]  V.Canvas                               │

│       正在分析正文…（约 10\\\\\\\\\\\\\\\~30 秒）      \\\\\\\\\\\\\\\[终止] │

└──────────────────────────────────────────────┘
```



* 阶段依次为：`正在分析正文…` → `正在绘制插画 n/N …` → `插画完成` / `失败原因`

* 点击「终止」会中断当前这轮（分析与出图请求都会被取消），卡片随即显示「已终止」

* **失败与「分析结果为空」也会显示在卡片上**，不会静默 —— 这是排查「什么都没发生」的主要入口

* 结束提示停留数秒后自动消失，失败提示停留更久；也可手动点「关闭」

* 卡片仅存在于 DOM，不写入聊天记录，也不进入上下文

## 八、查看插图提示词

插图使用的提示词**不出现在正文中，也不进入 AI 上下文**（`strip_marker` 默认开启，

标记在出图后即从 `mes` 中剔除）。需要查看时，**点击该插图**，浮层中会显示这条插图

对应的自然语言描述与 Danbooru 标签两段内容。



* 提示词随聊天记录一并保存（`extra.illust.src` 为含标记的完整原文），因此刷新、切换聊天后仍可查看；

* 标记按出现顺序与插图一一对应，浮层据此定位，无需额外存储；

* 浮层为插件自有的临时 DOM，关闭即销毁，不写入聊天记录；

* 采用点击触发而非悬停（移动端无悬停），也不使用 `title` 属性。

性能：点击监听以**事件委托**方式在页面加载时挂载一次，不为每张插图单独绑定；

提示词仅在点击时解析，渲染阶段无额外开销，也不发起任何模型调用或网络请求。

## 九、行为细节



* **独占一行**：图片为块级元素，将后续文字挤至下一行，不浮动、不环绕。

* **就地插入**：图片插入标记所在段落正下方，而非整条消息末尾。

* **后台串行**：出图在后台逐张进行，不锁定输入框，用户可继续对话。

  多张串行出于刻意设计 —— 并发易触发上游风控。

* **防重复**：已处理的消息标记 `extra.illust_done`，切换聊天 / 刷新 / 重渲染均不会重复触发出图。

* **失败可控**：某张失败时其标记原样保留，已出图片不重画；错误信息直接透传适配服务返回的

  message（该 message 已是可读文本：风控 / 内容策略 / 超时等）。

* **不污染聊天记录**：占位提示仅修改 DOM；失败也不会在聊天记录中留下「正在绘制…」残留。

## 十、已知限制



* `.mes_text img { display: block }` 为全局样式，

  会一并影响消息中其他 markdown 图片的排版（一律变为块级居中），属预期行为。

* 若手动编辑消息正文导致标记数量变化，插件会清除该条的插画状态（不重画，避免误触发出图消耗额度）。

* 第一版未提供「手动重绘」按钮。
